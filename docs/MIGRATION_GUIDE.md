# Migration Guide: CodeIgniter to Laravel

## Purpose

This guide defines a practical migration plan for moving the existing CodeIgniter support system to Laravel while preserving current business logic, user workflows, data, permissions, integrations, and operational behavior.

The current application is a completed support/helpdesk platform with public support portal, ticketing, knowledge base, chat, payments, client accounts, admin/staff permissions, settings, add-ons, and integrations.

## Migration Principles

- Preserve existing business behavior before improving implementation.
- Migrate by feature modules, not by files.
- Keep database compatibility during the first migration phase unless a controlled schema refactor is planned.
- Replace CodeIgniter global helpers and libraries with Laravel services, middleware, policies, form requests, events, jobs, notifications, and storage abstractions.
- Treat add-ons, payment gateways, AI integrations, email-to-ticket, and chat as high-risk manual migration areas.
- Maintain URL compatibility where possible, especially public ticket, knowledge, category, and payment links.

## CodeIgniter to Laravel Architecture Mapping

| Current CodeIgniter Area | Laravel Target |
|---|---|
| `application/controllers` | `app/Http/Controllers` |
| `application/controllers/admin` | `app/Http/Controllers/Admin` |
| `application/controllers/client` | `app/Http/Controllers/Client` |
| `application/models/database` | Eloquent models in `app/Models` |
| `application/views` | Blade templates in `resources/views` |
| `application/config` | Laravel config files and `.env` |
| `application/helpers` | Helper classes, service classes, or global helper files loaded by Composer |
| `application/libraries` | Laravel services, managers, facades, jobs, notifications, or packages |
| `APP_Controller` | Base controller plus middleware/view composers |
| `APP_Model` | Eloquent model base class or reusable traits |
| `APP_ConfirmController` | JSON/action controllers with standardized API responses |
| `APP_GridDataController` | Datatable/grid query services or API resources |
| `Session` library | Laravel session guards and session store |
| `ACL` library | Laravel policies/gates or package-backed permissions |
| Add-on hook system | Laravel events, listeners, service providers, or plugin contracts |

## Routing Migration

The current application uses limited explicit routes and relies heavily on CodeIgniter controller/method routing.

Current route behavior to preserve:

- Default route points to the public site homepage.
- `/admin` resolves to the admin dashboard.
- `/admin/{controller}` maps into admin controllers.
- `/a/{...}` maps to site add-on actions.
- `/common-script.js` serves dynamic JavaScript.
- Public routes include site pages, knowledge, categories, tickets, chat, user login/register/recover, social login, and payment callbacks.

Laravel recommendations:

- Define explicit route groups:
  - `routes/web.php` for public, client, admin, auth, payment callback, and content routes.
  - `routes/api.php` only for true API-style endpoints.
- Use route name conventions from the start.
- Use middleware groups:
  - `web`
  - `auth:client`
  - `auth:admin`
  - `can:*`
  - `csrf`
  - `signed` where secure ticket/payment links are needed.
- Preserve legacy URLs with route aliases or redirects where existing email links, payment links, and ticket tracking links depend on them.
- Recreate CSRF exclusions carefully for chat, add-on callbacks, admin chat, and payment/webhook-style endpoints.

## Authentication

The current system has separate concepts for:

- Admin/staff users from `app_user`.
- Clients and guest users from `site_user`.
- Guest ticket sessions.
- Social login.
- Remote login.
- Password reset flows.

Laravel target:

- Use multiple guards:
  - `admin` guard for `app_user`.
  - `client` guard for `site_user`.
- Use separate providers for admin and client models.
- Implement guest ticket access as signed/session-based access, not as a full authenticated guard unless required.
- Migrate password hashing carefully. Existing passwords appear to use legacy MD5-style hashing with user ID salt. Laravel must support legacy verification and rehash passwords on successful login.
- Preserve client registration, password recovery, social login, and remote login behavior.

Manual migration required:

- Admin login lockout logic.
- Client login/registration enable-disable settings.
- Guest ticket access by email and ticket tracking ID.
- Existing social session data handling.
- Password reset email templates.
- Legacy password compatibility.

## Authorization

The current authorization system is resource/page based using roles and role access records.

Laravel target:

- Implement a custom permission layer using Gates or Policies backed by existing `role_list`, `role_access`, and `page_list`.
- Preserve existing permission keys during the first migration.
- Create middleware equivalent to current `CheckPageAccess`.
- Support super user roles through the existing role grade behavior.
- Preserve permission checks for admin grids, actions, status toggles, delete actions, role management, and settings.

Manual migration required:

- Permission matrix UI.
- Dynamic page/resource list.
- Role access toggle behavior.
- Super user restrictions.
- Role grade restrictions when creating/editing admin users.

## Risks and Breaking Changes

### High Risk

- Legacy password hashing.
- Admin/client dual authentication.
- Role and permission behavior.
- Guest ticket access and attachment authorization.
- Payment callbacks and transaction idempotency.
- Email-to-ticket parsing.
- Add-on hook behavior.
- Chat real-time/session behavior.
- Dynamic settings stored in database.
- Existing public links in emails.

### Medium Risk

- jQGrid/admin list behavior.
- Popup-based form flows.
- Custom field validation.
- API-backed custom fields.
- Theme and custom CSS/JS handling.
- Knowledge/category SEO metadata.
- GDPR data export/delete behavior.
- Timezone handling.

### Likely Breaking Changes

- URL suffix behavior using `.html`.
- CSRF behavior on AJAX and external callback endpoints.
- Session key names.
- File paths and download URLs.
- Direct use of global helper functions.
- Inline PHP view assumptions.
- Add-on controller/action dispatching.
- Dynamic JavaScript endpoints.

## Laravel Best Practices to Apply

- Use Form Requests for validation.
- Use Policies/Gates for authorization.
- Use Events and Listeners for ticket lifecycle actions.
- Use Notifications for email and on-screen notification workflows.
- Use Queues for email sending, email-to-ticket processing, AI calls, and external API calls.
- Use Storage disks for private and public files.
- Use signed URLs for protected file and ticket links.
- Use Blade components for shared UI modules.
- Use config files for defaults and database settings for admin-editable values.
- Use service classes for integrations and payment gateways.
- Use database transactions for ticket creation, replies, payments, and user creation.
- Use idempotency checks for payment processing.
- Add model casts and accessors only after verifying stored data formats.
